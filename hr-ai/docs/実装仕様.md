# hrai 実装仕様（v0.1.0 / フェーズ1＋フェーズ2の一部）

`SPEC.md` の方針に沿った実装。Python 標準ライブラリのみ（Anthropic API は urllib で呼び出し）。

## 構成
| ファイル | 役割 |
|---|---|
| hrai/regs.py | 規程（条番号つきMarkdown）の読込、**引用の原文照合** |
| hrai/bot.py | 規程Bot。回答生成→引用検証→記載なし/回答/拒否の決定、ログ記録 |
| hrai/guard.py | 個人の給与・評価・健康、個別の懲戒・休職可否、法律相談を検出して拒否 |
| hrai/pii.py | メール・電話・郵便番号・生年月日・12桁番号・「〇〇さん」の検出とマスク |
| hrai/drafts.py | 求人票・面接質問・通達・退職チェックリストの下書き、承認フロー |
| hrai/db.py | SQLite ログ（qa_log, drafts）。`HRAI_DB` で保存先変更 |
| hrai/roi.py | 削減時間・金額の試算 |
| hrai/evaluate.py | 50問ゴールデンテスト（合格基準つき） |
| data/settings.json | 社名・問い合わせ先・ROI係数 |
| data/sample_regulations/ | 架空の規程3本（本番規程は `data/regulations/` に置くと優先される） |

## 規程Bot
1. 質問の個人情報をマスク（以降の処理・LLM入力・ログはマスク後）
2. `guard` に該当 → **LLMを呼ばず**拒否し、担当者へ案内
3. LLM（Claude／キー無し時は簡易検索モック）が JSON で結論・引用を返す
4. **全引用が、指定した規程・条の本文の部分文字列か検証**。1件でも不一致なら回答を破棄し「規程に記載がありません」
5. 回答の型: 結論／根拠（規程名・条番号・原文）／注意点／確認先／規程の改訂日
- 外部検索・送信・編集の権限なし（読み取りのみ）
- 規程が短い間は全文をコンテキストに載せる（RAGなし）
- モデルは環境変数 `LLM_MODEL`（既定 `claude-sonnet-5-5`）

## 下書き承認フロー
`draft new` → 自動チェック（差別につながる表現、個人情報パターン、`【要入力】` 残り）→ 人が `edit` → `approve --by 氏名`。
- フラグが残る下書きは**承認不可**。承認者名が必須。二重承認不可。
- 承認時に `out/approved/` へ承認者・日時つきで書き出し、本文のハッシュを記録する。

## 送信（文面の確認は人、送信はシステム）
`draft send ID --via slack|email [--to 宛先] [--dry-run]`（`hrai/sender.py`）。送信できるのは次をすべて満たす場合のみ。
1. 人が承認済み（未承認・却下は不可）
2. 未送信（二重送信不可）
3. 承認後に本文が変わっていない（ハッシュ一致。承認後の編集は再承認が必要）
4. フラグ無し（個人情報・差別表現・未入力）
5. メール宛先が `data/settings.json` の `allowed_email_domains` 内
- 送信手段: Slack Webhook（`HRAI_SLACK_WEBHOOK`）、SMTP メール（`HRAI_SMTP_HOST` / `PORT` / `USER` / `PASSWORD` / `HRAI_MAIL_FROM`）。認証情報は環境変数のみ。
- 送信結果（日時・手段・宛先）は `drafts` テーブルに記録。`--dry-run` は何も送らず内容だけ表示。
- 規程Bot（質問回答）自体は引き続き読み取り専用で、送信機能を持たない。

## 勤怠・有給アラート（`hrai/attendance.py`）
`attendance check --month 2026-10 --today 2026-10-27`。勤怠CSV（employee,date,clock_in,clock_out,break_min,leave）と社員ディレクトリ（`data/hr/`、Git管理外）から判定。
- 判定はすべてコードの数値計算（AIは使わない）。文面は固定テンプレート
  1. 勤怠の未入力（平日・祝日設定を除く、今日より前の日で記録なし）
  2. 残業の月末見込み（現在値÷経過営業日×月の営業日）が社内の目安（`overtime_warn_hours`）超
  3. 有給の取得が最低日数（`paid_leave_min_days`）未満で、年度末まで`alert_months_before_year_end`か月以内（付与日数が`paid_leave_obligation_min_grant`以上の社員のみ）。CSV期間より前の取得日数は `leave_taken_before`
- しきい値は `data/settings.json` の自社設定（法令値はコードに埋め込まない）。本人宛と、残業・有給のみ上長宛の下書きを作成（承認待ち、同日同宛先の重複作成なし）
- 一括承認 `draft approve-all --kind attendance_alert --by 氏名`（固定テンプレートの社内通知のみ対象）→ `draft send-all --kind attendance_alert --via email [--dry-run]`

## 入社手続き（`hrai/onboarding.py`）
`onboarding start 社員ID --start-date 2026-11-01 --email 宛先` で、本人向け「入社のご案内」と総務向けチェックリストの下書きを作成。項目と期限は `data/onboarding_template.json`。
- `onboarding status` / `done 社員ID 項目名 --by 氏名` / `remind --today 日付`（期限超過の本人宛・総務宛の催促を下書き化）
- 社会保険・雇用保険などの届出項目は `human_only`。システムは期限管理のみで、完了は人が記録する（自動で完了にならない）

## 求人応募の一次対応（`hrai/recruit.py`）
`recruit reply 応募JSONL`（id,email,position,subject,body）。受付返信・FAQ回答・面接日程の候補までを下書き化。
- FAQは規程Botと同じ「原文引用の検証」を通ったものだけ使用（`data/recruit/` に募集FAQを置く。無ければ架空サンプル）
- 合否・年収・条件交渉の問い合わせは回答せず担当者へ回し、日程候補も出さない。選考・評価・合否判断は行わない
- 応募者宛は1件ずつ承認。送信は応募メールの送信元アドレス宛・メールのみ（ドメイン許可リストの対象外、宛先固定）。不正なアドレスの応募は下書きを作らない

## 1on1 準備シート（`review prep`）
`review prep 社員ID --period 2026-04:2026-09 --by 氏名`。前回の未完了の約束事、日報の原文引用、話題の候補を下書き化。評価ではなく対話の材料。評価根拠シートと同じ制限（点数・処遇推奨の禁止、要配慮情報の除外、送信不可、閲覧記録）を適用。

## Slack 連携（`hrai/slack_app.py`）
- `slack serve --port 3000`: `/slack/command`（`/hr 質問` → 規程Bot、回答は質問者のみ表示）と `/slack/interact`（承認・却下ボタン）を受信
- `slack notify --channel C…`: 承認待ちの下書きを承認ボタン付きで投稿（承認は承認のみ。送信は別操作）
- セキュリティ: Slack署名（HMAC-SHA256）の検証と5分の期限、承認者は `data/settings.json` の `slack.approvers` に登録したユーザーのみ、評価関連の下書きは投稿もボタン操作も不可、質問文はサーバーログに出さない
- 環境変数: 署名検証用 `SLACK_SIGNING_SECRET`、投稿用 `SLACK_BOT_TOKEN`（値はコード・文書に書かない）。Claude利用時は3秒制限のため、先に「確認しています」を返し回答を後から投稿

## 人事評価の支援（点数なし・根拠整理と下書き）
`review build 社員ID --period 2026-04:2026-09 --by 評価者名`（`hrai/evaluation.py`）。評価の判断と最終コメントは評価者（人）が行う。
- **入力**（`data/eval/` に配置、Git管理外。社員IDで仮名化したJSONL。無ければ架空の `data/sample_eval/`）
  - `daily_reports.jsonl`（社員ID・日付・日報）／`mentoring.jsonl`（育成者・育成相手・日付・時間・種別）／`outcomes.jsonl`（社員ID・指標・開始値・終了値）
- **評価基準**（`data/eval_criteria.json`で変更可）: 成果／育成・貢献（教育した量と、育成した相手の成果の変化）／日々の取り組み（日報）
- **出力**（評価根拠シート＝承認待ちの下書き）
  1. 事実: 日報件数（月別）、育成回数・時間・相手人数、指標の変化（差と%）。**数値はコードで計算し、AIは作らない**
  2. 日報の原文引用つき整理。**引用が日報原文に実在するかをコードで検証**し、不一致は破棄
  3. 評価コメント案（軸ごと）。点数・ランクは付けない
  4. 評価者への確認事項（除外した要配慮情報の件数、日報が少ない場合の注意、直近偏重・比較禁止の注意）
  5. 評価者の最終コメント欄（`【要入力】`のままでは承認不可）
- **コードで強制する禁止事項**: 点数・ランク・評価区分・順位／昇給・降格・懲戒等の推奨／他の社員との比較／要配慮情報（健康・家庭・休職・年齢・国籍など）は、承認前チェックで検出して承認不可
- **データ保護**: 要配慮情報を含む日報の文はAI入力前に除外、氏名等はマスク、他の社員の日報は含めない。シートの閲覧は評価者名つきで `eval_access` に記録。評価文書は**送信機能の対象外**（`out/evaluations/` に保存）
- 育成相手の成果の伸びは「他の要因を含む参考情報」であり、因果とみなさない旨をシートに明記

## 届出は人が行う（実装していない）
社会保険・雇用保険・労基署などへの届出の作成・提出機能は存在しない。退職チェックリストにも「人が専用ソフト/e-Govで実施」と明記。

## AIにさせないこと（実装していない）
給与・保険料の計算、届出の提出、採否・評価・懲戒の判断、法律相談。

## 品質ゲート（`python3 -m hrai.cli eval`）
| 種類 | 問数 | 基準 |
|---|---|---|
| 規程に答えがある | 30 | 95%以上（引用が期待の条を含む） |
| 規程に答えがない | 10 | 100%「記載なし」 |
| 個人情報・判断を求める | 10 | 100%拒否 |

現状（簡易検索モック）: 30/30, 10/10, 10/10。**この結果は架空規程＋モックでのもの。自社規程・Claude に切り替えたら必ず再実行し、社労士レビューを受けること。**

## 既知の制約
- 氏名の検出は「〜さん/様/氏」付きのみ。単独の氏名は検出できない（利用者教育が必要）
- ゴールデン50問は架空規程用。自社規程用に差し替えが必要
- モックは語彙一致ベースで言い換えに弱い（Claude利用で改善見込み、要再評価）
- 労務SaaS・Slack・e-Gov連携は未実装（フェーズ3）。入口はCLIのみ
- 拒否判定は正規表現。見逃し・過剰拒否があり得るため、ログを定期確認すること
- Slack連携・メール送信は実環境での接続試験が未実施（署名検証・承認処理・投稿のロジックは単体テスト済み）。導入時に必ず実環境で確認すること
- 勤怠アラートは勤怠CSVの形式が前提。自社の勤怠ソフトの出力に合わせた変換が必要な場合がある
- 評価支援: 簡易モードの日報分類はキーワード一致で精度が低い（Claude利用を推奨）。要配慮語の除外もキーワード方式で見落としがあり得るため、評価者が目視確認すること。外部AIへ日報を渡す場合は個人情報保護法上の整理（利用目的の特定・委託/第三者提供の扱い）が必要
- 法令の数値はプロンプトに埋め込んでいない（根拠は自社規程のみ）
