# hrai 取扱説明書

## 1. 準備
- Python 3.9 以上（`python3 --version`）。追加インストール不要
- 作業場所: `hr-ai/` フォルダで実行
- Claude を使う場合のみ: 環境変数 `ANTHROPIC_API_KEY` を設定（キーはコミット・チャット貼り付け禁止）。モデル変更は `LLM_MODEL`
  - 未設定でも動作（簡易検索モード）。本番では Claude を推奨
- 利用前に SPEC.md 第6章のツール設定チェック（学習利用オフ、会社契約、ログ確認）を人が確認し記録すること

## 2. 自社規程の登録
1. 規程を条番号つき Markdown にして `data/regulations/` に置く（個人情報を含めない）
```
規程名: 就業規則
改訂日: 2026-04-01

## 第7条（年次有給休暇の付与）
本文…
```
2. `data/settings.json` の `contact`（問い合わせ先）と `company_name` を編集
3. 置くと架空サンプルより自社規程が優先される。規程は `.gitignore` によりGit管理されない
4. **`tests/eval/golden.json` を自社規程の50問に差し替える**（答えあり30／なし10／拒否10）

## 3. 使い方
| やりたいこと | コマンド |
|---|---|
| 質問する | `python3 -m hrai.cli ask "有給休暇は半日で取れますか"` |
| 求人票の下書き | `python3 -m hrai.cli draft new job_posting -p title=経理担当 -p duties=記帳 -p requirements=経験者 -p conditions=週5日` |
| 下書きの種別 | job_posting / interview_questions / notice / offboarding_checklist |
| 下書き一覧・確認 | `draft list` / `draft show 1` |
| 修正（編集後のテキストを渡す） | `draft edit 1 修正版.md` |
| 承認（保存） | `draft approve 1 --by 総務太郎` → `out/approved/` |
| 送信（承認済みのみ） | `draft send 1 --via email --to 宛先` または `--via slack`。先に `--dry-run` で確認 |
| 却下 | `draft reject 1 --by 総務太郎 --reason 理由` |
| 評価根拠シートの作成 | `python3 -m hrai.cli review build E01 --period 2026-04:2026-09 --by 評価者名`（作成後は `draft show/edit/approve` で扱う） |
| 品質テスト | `python3 -m hrai.cli eval`（規程更新・モデル変更のたびに必須） |
| 削減効果 | `python3 -m hrai.cli report` |
| 単体テスト | `python3 -m unittest discover -s tests` |

※ `draft` 系は `python3 -m hrai.cli draft new ...` のように `draft` を付けて実行します。

## 3-2. 人事評価の支援（点数なし）
1. データを用意（社員IDで仮名化。氏名とIDの対応表は人事が別管理）し、`data/eval/` に置く（Git管理外）
   - `daily_reports.jsonl` 例: `{"employee":"E01","date":"2026-05-13","text":"手順書の改善案を提案した。"}`
   - `mentoring.jsonl` 例: `{"mentor":"E01","mentee":"E02","date":"2026-04-22","hours":1.5,"kind":"OJT","note":"請求処理"}`
   - `outcomes.jsonl` 例: `{"employee":"E02","metric":"月間処理件数","start":40,"end":58,"unit":"件","from":"2026-03","to":"2026-09","note":""}`
2. `review build E01 --period 2026-04:2026-09 --by 評価者名` で根拠シートを作成（閲覧が記録されます）
3. `draft show ID` で内容を確認。第2章の引用と第1章の数値を、元データと照らして確認する
4. 評価者が第5章「最終コメント」を記入し、`draft edit ID 修正版.md` → `draft approve ID --by 評価者名`
5. 承認済みシートは `out/evaluations/` に保存されます（**送信はできません**）。本人へのフィードバックは人が行う
- **点数・ランク・順位・昇給の推奨・他者との比較・要配慮情報**を書くと承認できません
- 評価基準を変える場合は `data/eval_criteria.json` を編集し、事前に社員へ周知してください

## 3-3. 勤怠・入社・応募・1on1・Slack
| やりたいこと | コマンド |
|---|---|
| 勤怠アラートの作成 | `python3 -m hrai.cli attendance check --month 2026-10 --today 2026-10-27`（勤怠CSVと社員ディレクトリを `data/hr/` に置く） |
| 内容を確認して一括承認・送信 | `draft show ID` で確認 → `draft approve-all --kind attendance_alert --by 氏名` → `draft send-all --kind attendance_alert --via email --dry-run`（問題なければ `--dry-run` を外す） |
| 入社者の登録 | `onboarding start E10 --start-date 2026-11-01 --email 宛先` |
| 入社手続きの進捗・完了記録 | `onboarding status E10` / `onboarding done E10 "項目名" --by 氏名` |
| 期限超過の催促 | `onboarding remind --today 2026-11-03`（下書きを作成。承認後に `draft send-all --kind onboarding_reminder`） |
| 応募への返信 | `recruit reply 応募.jsonl` → `draft show ID` で確認 → `draft approve ID --by 氏名` → `draft send ID --via email`（宛先は応募者のアドレスのみ） |
| 1on1の準備 | `review prep E01 --period 2026-04:2026-09 --by 上長名` |
| Slack受信の起動 | `slack serve --port 3000`（Slackアプリの Request URL に `/slack/command` と `/slack/interact` を設定） |
| 承認依頼をSlackへ投稿 | `slack notify --channel チャンネルID` |

- 勤怠CSVの列: `employee,date,clock_in,clock_out,break_min,leave`（leave は 有給 / 半休）。社員ディレクトリ `directory.json` に連絡先・上長・有給付与日数を記載
- しきい値（残業の目安時間、有給の最低日数、祝日、面接日程の候補）は `data/settings.json` で自社に合わせて設定
- Slack: 環境変数 `SLACK_SIGNING_SECRET`（署名検証）と `SLACK_BOT_TOKEN`（投稿）を設定し、`data/settings.json` の `slack.approvers` に承認者のSlackユーザーIDと氏名を登録
- 一括承認は固定テンプレートの社内通知のみ。**応募者宛の返信は1件ずつ内容を確認して承認**する
- 入社の届出（社会保険・雇用保険等）は人が実施し、`onboarding done` で完了を記録する

## 4. 回答の見方
結論／根拠（規程名・条番号・原文）／注意点／確認先／規程の改訂日。
- 「規程に記載がありません」: 規程に無い、または引用の検証に失敗した場合。担当者へ確認
- 「お答えできません」: 個人情報・判断・法律相談。担当者へ相談

## 5. 導入ステップ
| 段階 | 内容 | 次へ進む条件 |
|---|---|---|
| 0 | ツール設定確認、情報分類、社労士へ方針共有 | チェック完了 |
| 1 | 自社規程登録、50問テスト、社内試験運用 | `eval` 合格、重大な誤り0件 |
| 2 | 下書き承認フローを実運用（誤送信0件を確認） | 削減時間を実測 |
| 3 | 労務SaaS／Slack連携を検討 | 半年ごとの見直し |

## 6. 運用ルール
- 質問に氏名や個人情報を入力しない（検出時は警告し、ログはマスク）。入力してしまったら社内に記録・報告
- 規程を変更したら、労働者代表の意見聴取と届出（労基法89・90条）を人が行い、その後 `改訂日` を更新して `eval`
- 文面の確認と承認は人が行う。送信は承認後にシステム（`draft send`）が行う。承認後に本文を直すと再承認が必要
- 送信前に必ず `--dry-run` で宛先・件名を確認する（最初の数回は特に）
- 送信設定: 環境変数 `HRAI_SLACK_WEBHOOK`（Slack）、`HRAI_SMTP_HOST` / `HRAI_SMTP_PORT` / `HRAI_SMTP_USER` / `HRAI_SMTP_PASSWORD` / `HRAI_MAIL_FROM`（メール）。メールの宛先ドメインは `data/settings.json` の `allowed_email_domains` に登録（既定は example.com のみ）
- 人事評価に使う場合は、事前に①評価基準と、AIが根拠整理・下書きを行うことを社員へ周知、②本人へ根拠の開示・説明ができる運用、③評価制度・利用目的の規程化、④外部AIへ日報を渡す際の個人情報保護法上の整理を、社労士・弁護士と確認する
- 評価データ（日報・育成記録・成果指標）は `data/eval/` に限定し、アクセスできる評価者を絞る。AIの根拠整理は参考であり、評価者は必ず元データを確認する
- 勤怠アラートは、社員への通知であり評価・処分には使わない旨を周知する。残業・有給の数値は目安で、最終確認は勤怠システムで行う
- 応募者に送る前に、返信下書きの内容（FAQの引用、日程候補）を必ず確認する。選考結果の連絡はシステムで行わない
- Slack連携・メール送信は、導入時に実環境でテスト（テスト用チャンネル・自分宛）してから本運用にする
- 届出（社会保険・雇用保険・労基署等）はシステムでは行わず、人が専用ソフト／e-Govで行う
- `logs/hr_ai.db`（質問・回答・引用・承認者）は定期確認し、拒否／記載なしが多い質問は規程やFAQの改善に使う
- 半年ごとにモデル・料金・法改正を見直す

## 7. 困ったとき
| 症状 | 対処 |
|---|---|
| 答えがあるはずなのに「記載なし」 | 規程に条文があるか確認。簡易検索モードなら言い換えに弱いので Claude を設定 |
| `draft approve` が拒否される | 表示されたフラグ（未入力・差別表現・個人情報）を `edit` で解消 |
| `eval` が不合格 | NG の質問を確認。規程・モデル変更が原因なら反映せず、原因を分析 |
| 回答の engine が mock のまま | APIキー未設定、または通信失敗（自動で簡易検索に切替） |

## 8. 他社へ提供する場合
自社以外に提供して報酬を得る場合、社労士法・弁護士法に触れる可能性があります。**提供前に社労士・弁護士へ確認してください**（SPEC.md 第6章）。
